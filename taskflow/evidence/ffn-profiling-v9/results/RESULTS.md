# Whole-program FFN profiling and joint-search feedback v9

The original M128 FP32 FFN takes about581.6s because it executes sixteen complete
M8 programs, each with three expensive GEMMs on one compute core and four serial
device stages. It is not sixteen concurrently executing replicas. The independent
stage measurements account for approximately the full-program time. Host staging,
submission and partition bookkeeping account for a very small fraction of the
recorded wall. XRT wait remains a combined runtime/device interval: its contents
cannot all be labeled computation.

A supported implementation choice now keeps the original scalar FP32 products
and uses eight independent vector-add lanes. It preserves K order and the finite
`atol=rtol=1e-5` contract. M1/M5/M8 full programs pass three seeds. A new complete
M128 single-seed diagnostic passes in541.869801s, compared with581.584170s for the
original same seed. This is a6.83% observed reduction; the new long run is not a
new three-seed M128 acceptance. Original three-seed acceptance remains frozen.

## Stage measurements and bottleneck order

These are independent complete-main programs, not timestamps inside a full ELF.
Baseline M1/M5/M8 each have one seed, one warmup and two hot repeats. Optimized
M8 stages/full have one seed, one warmup and one hot repeat, under the same
compiler configuration. All stage outputs are independently rechecked.

|1 scalar|1540.664|1539.462|12.097|1539.234|4628.898|
|5 scalar|7655.155|7654.991|56.862|7654.204|23017.667|
|8 scalar|12086.535|12085.712|92.815|12086.387|36345.460|

The optimized independent-stage sum is33861.641ms,2.977ms above its full call.
This difference includes separate contexts and firmware boundaries; it does not
isolate a fusion or per-stage configuration cost. Activation remains scalar;
the actual full-program activation core text is identical to the baseline.

The strongest bottleneck evidence is the three GEMMs' approximately linear M
scaling, matched stage/full time, actual single-core allocation and hot-path
software products. Gate/Up/Down have180355072 products each per M8. Their actual
executed core code calls `__mulsf3` in the K loop; scalar additions already use
native vector-add instructions with one useful lane. Four static helper call
sites in unrolled scalar code are not four total calls: the source count gives
541065216 products per M8 and8657043456 per M128. Full-program MACs use this
count; reported FLOPs are2×MACs and exclude activation arithmetic. Original M8
throughput is0.02977 GFLOP/s on complete host wall, not peak device throughput.

Software multiplication is therefore a strong optimization target, but its
exclusive cycle fraction is not measured. The selected change reduces add/loop
overhead while retaining every product. The remaining scalar product workload
explains why this is a modest improvement. DMA/lock/firmware time inside wait
cannot be exactly separated. Host submission/partition overhead is far too small
on these recorded boundaries to explain hundreds of seconds.

## Why44.4% fewer planned bytes did not establish a speedup

The N16 phase-local and B-panel retained programs move221184 and122880 planned
bytes; B bytes fall131072→32768. Native regions/counts match generated transfers.
Payload rises3584→9728B under the unchanged24576B policy budget, with a separate
4096B reserved stack. They have two versus five serial device stages, but each
complete program still has one XRT start/wait. The extra stages do not mean five
host submissions.

Three seeds, two warmups and ten hot repeats per candidate were interleaved in
both detailed and minimal observer sessions. Detailed medians are18.719868 and
18.641660ms; minimal medians18.686514 and18.658470ms. Median paired differences
are−0.013870 and−0.000460ms; ranges extend about−0.70..+0.73ms. No statistically
supported residency speedup or equivalence is claimed. Sessions are not a matched
observer-overhead experiment, and no samples/outliers were removed.

The old theoretical model prices the98304B saving at only0.0098304ms using its
assumed10GB/s. That is an assumption, not measured bandwidth; it is small relative
to the observed compute-heavy call and timing variation. Added stage/configuration
work could offset it, but no isolated stage-cost experiment proves that cause.
Actual selected polling and its0.0002s configured interval are recorded for new
runs. Older missing selections remain unknown. Frequency was not locked and no
physical DDR byte counter was available. Planned bytes are never labeled measured
DDR traffic or host BO copies.

## Correctness and the implementation decision

The public plan chooses `scalar-product-vector-add-f32`, lanes8, for eligible
independent loops. Math tasks and initializers remain explicit scalar entries.
Source analysis proves independent contiguous spatial accesses; generic MLIR
vectorization supplies the body. Products/divisions are scalarized through the
existing toolchain FP32 helpers, while independent adds/subtracts stay vectorized.
There is no BF16 conversion, FMA, fast-math flag or K reassociation. No new runtime
or CPU computation path was introduced. The installed XRT runner is imported from
the toolchain's multilaunch package; no Triton computational recipe is used.

| Complete program | scalar hot median ms | mixed8 hot median ms | observed reduction |
|---|---:|---:|---:|
|M1|4628.467|4287.246|7.37%|
|M5|23017.722|21200.528|7.89%|
|M8|36346.210|33863.542|6.83%|

Each row is three seeds, one warmup and one hot sample per implementation/seed,
with forward/reverse ordering. The raw hot ranges are saved; these are paired
experiments, not universal performance guarantees. Maximum absolute reference
errors are1.28e-8,2.42e-8 and1.75e-8 respectively. The new full M128 has max absolute
error2.14e-8, normalized L2 error2.22e-6, max relative error0.00360 for
`abs(reference)>=1e-6`, and near-zero max absolute error6.14e-9. Relative error is
diagnostic; acceptance remains the original combined absolute/relative rule.
All18 observed M1/M5/M8 scalar-versus-mixed full-output pairs, plus the original
versus new M128 output, are bit-identical. This is an observation for tested
inputs, not a proof for arbitrary FP32 values.

M5/K129/N16 with M2/K64 tiles and oversized generic64×64 add→scale both pass
three seeds/two warmups/three hot repeats. The latter is a generic body, not a
GEMM-specific generator. Full M8 planned transfer volume remains306176000B and
payload20480B for both implementations; backend tensor scratch/padding addition
is zero in the physical audit. Four stages still use the same core(0,2).
Stack high-water and physical lane utilization are not measured.

Earlier lane4 compilation failure and mixed r2 timeout are preserved. The r2
root cause was inconsistent loop traversal: generic analysis used preorder but
vector lowering collected loops in postorder, shifting the wrong axes. The fix
uses source-loop identities, a checked bijection and original bound/step checks.
Actual A(i,k), B(k,j), C(i,j) SSA checks and mutated-index/recurrence negatives
guard it. Installed lane4 support is rejected explicitly. A separate four-input
multi-phase stream-order failure is also preserved and narrowly rejected by the
target capability checker; packed two-input controls pass. This does not claim
the general four-input downstream backend has been repaired.

## Trace and verification boundaries

`packet-trace-marked-r2` supplies one complete ordered single-core bracket for
1×64×16 scalar GEMM:124209 device cycles with1024 vector-event pairs. The output
is independently correct, with on/off controls. Device cycles have no calibrated
physical clock mapping; the Perfetto cycle view is a surrogate axis. It covers
that compute bracket, not all cores, DMA, FFN or DDR traffic. There is no overflow
counter; zero buffer suffix alone is not proof of lossless trace capture.

`packet-trace-mixed-r1` has14 correct on/off outputs, but its end marker is absent.
It remains a partial trace and supplies no valid optimized cycle count. Its
host medians0.425520/0.428919ms are noisy total diagnostic perturbation, not an
isolated trace cost. The earlier invalid marked trace and decode failures are
retained. Host `host-timeline.json` files are API timelines, not device traces.

Relevant regression results:31 compiler groups covering independent Core,
original Amoeba/search, mapping and AIR;47 C++ cost contracts;9 mixed-lowering
checks; stream-capacity negatives;8 real CGRA model contracts; fitter18 boundary
checks including legacy byte compatibility; checkpoint7, collector11 and final
BO-context14 checks;
fresh-workflow12 CPU protocol checks. Two final CPU-entry runs use an isolated
existing build directory; fresh-output and mock workflow behavior pass, but the
entire new `all` wrapper was not rerun from a cold build. The actual hardware,
fit/freeze/holdout and feedback commands above ran separately with saved
identities. Core continues to link no AIR/AIE/XRT/Neura runtime libraries.

## Reproduction

From a clean shell in the sibling artifact repository, with the existing installed
LLVM/AIE/XRT environment available:

```sh
bash taskflow/scripts/run_taskflow_ffn_profiling_v9.sh cpu /tmp/orbit-v9-cpu-NEW
bash taskflow/scripts/run_taskflow_ffn_profiling_v9.sh all /tmp/orbit-v9-base-NEW
bash taskflow/scripts/run_taskflow_ffn_optimization_v9.sh \
  /tmp/orbit-v9-base-NEW /tmp/orbit-v9-opt-NEW --stages --m128 --trace
```

All output directories must be new. The default build is external to Core;
`ORBIT_SRC`, `LLVM_BUILD`, `AIE_TOY_ROOT`, `ORBIT_TEST_PYTHON` and
`ORBIT_BUILD_ROOT` are supported. CPU mode never opens the device. The baseline
entry supports separate collect/freeze/holdout/audit phases and checks model
identity before/after holdout execution. Optimization checks audited baseline
state and freeze identity, then source/full-plan/AIR/ELF consistency before joint
device profiling. See [validation details](taskflow-ffn-profiling-v9-validation.md),
[code analysis](taskflow-ffn-code-profile-v9.md),
[model boundary](direct-air-cost-v9.md) and
[native search](profiled-native-search-v9.md).

Remaining limits are explicit: no calibrated multi-core or mixed implementation
predictor, no arbitrary cross-stage SRAM sharing, no full FFN device trace or
physical DDR counter, no repaired general four-stream multi-phase transport, and
no new three-seed optimized M128 long acceptance. None substitutes for the complete
program executions reported above.
